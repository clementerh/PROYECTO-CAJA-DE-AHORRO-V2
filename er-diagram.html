Explicación tabla por tabla

🔐 usuario MODIFICADA

Se agregaron clave_hash (para autenticación segura con hash SHA256), rol (admin, operador, consulta) y activo. Ahora se conecta con prestamo vía id_usuario_registro para saber quién registró cada operación. Esto resuelve el problema de trazabilidad y auditoría.

👥 afiliados MODIFICADA

Se agregó condicion (jubilado, contratado, ordinario) como pidió la secretaria. También fecha_ingreso a la caja de ahorro y activo para baja lógica. La cédula se mantiene como campo UNIQUE para búsquedas rápidas (consulta por cédula del asociado).

🏦 prestamo MODIFICADA

Es la tabla con más cambios. Se agregó monto_aprobado (diferente al solicitado, como indicó la entrevista), num_cuotas y monto_cuota (se calculan UNA vez y se guardan, sin recálculo), periodicidad (mensual o quincenal), estado (activo, pagado, cancelado) e id_usuario_registro para auditoría. Se eliminó id_cuota como FK porque la cuota ya no es un catálogo sino un valor calculado.

📅 plan_pago NUEVA — reemplaza la tabla "cuota"

Esta es la tabla de amortización. Se genera automáticamente al aprobar un préstamo. Cada fila es una cuota con su desglose: capital, interés, monto total y saldo restante. El campo pagada indica si ya se cubrió. Cuando un asociado hace un abono extra, se marcan cuotas como pagadas (se reduce el tiempo, NO se recalcula). Esto garantiza que el saldo quede en 0,00 Bs exacto al final.

💸 detalles_prestamo MODIFICADA

Ahora se vincula con plan_pago para saber a qué cuota específica corresponde cada pago. Se agregó tipo_pago (cuota regular, abono extra, descuento nómina) y observacion. Es el registro real de cada pago realizado.

🪙 aportes NUEVA

El objetivo principal de la caja de ahorro es el ahorro sistemático. Esta tabla registra los aportes mensuales de cada afiliado. Se necesita para el reparto de fin de año y para los balances trimestrales que pide auditoría.

📊 tasa MODIFICADA

Se agregó fecha_vigencia, descripcion y activa. Aunque hoy la tasa es fija al 8%, esto permite registrar cambios históricos (si mañana cambia, no se pierde la tasa con la que se calcularon préstamos anteriores).

📋 haberes MODIFICADA

Se reemplazó la FK a la tabla meses por campos directos anio + mes (enteros). Mucho más simple y funcional. Registra los haberes mensuales del afiliado para calcular capacidad de pago.

💰 sueldo_base + sueldo_base_afiliado MODIFICADAS

Se mantiene la relación N:N del profesor. Se agregó fecha_desde en la tabla intermedia para saber cuándo se asignó cada sueldo. Esto es clave para la validación del 33.33% — el sistema necesita el sueldo base vigente para verificar si el afiliado puede endeudarse.

📆 meses ELIMINADA

Se eliminó esta tabla. Era innecesaria — los meses se manejan directamente como campos INT (1-12) en las tablas que lo necesitan. Esto simplifica consultas y evita JOINs innecesarios.

Comparación: diseño del profesor vs propuesta

Tablas del profesor (original)

Se mantienen (con mejoras)

  • usuario → + rol, clave_hash, activo
  • afiliados → + condicion, fecha_ingreso, activo
  • sueldo_base → igual
  • sueldo_base_afiliado → + fecha_desde
  • tasa → + fecha_vigencia, activa
  • prestamo → + muchos campos nuevos
  • detalles_prestamo → + tipo_pago, id_plan_pago
  • haberes → se usa anio+mes en vez de FK a meses

Cambios estructurales

  • cuota (catálogo) → se transforma en plan_pago
  • meses → se elimina (innecesaria)
  • aportes → tabla nueva (esencial)
  • usuario ahora conectada con prestamo

Reglas de negocio cubiertas por la propuesta

✅ Ahora cubierto

  • Validación del 33.33% del sueldo base
  • Monto solicitado ≠ monto aprobado
  • Cuotas iguales, consecutivas, sin recálculo
  • Saldo final exacto en 0,00 Bs
  • Periodicidad quincenal o mensual
  • Abono extra reduce tiempo, no recalcula
  • Condición del asociado (jubilado, contratado...)
  • Consulta por cédula con historial
  • Aportes mensuales para reparto anual
  • Balances trimestrales y auditoría anual
  • Trazabilidad (quién registró qué)

❌ No cubierto en el original

  • No había campo estado en préstamo
  • No diferenciaba solicitado vs aprobado
  • Cuota era catálogo estático
  • No había tabla de amortización
  • No había aportes
  • No había periodicidad
  • No había condición del asociado
  • Usuario desconectada del sistema
  • Haberes sin año
  • No había auditoría ni roles

Resumen cuantitativo

Original del profesor

  • 10 tablas
  • ~30 campos en total
  • 0 validaciones de negocio en BD
  • 0 campos de auditoría

Propuesta mejorada

  • 9 tablas (1 menos, más eficiente)
  • ~60 campos en total
  • Soporta todas las reglas de la entrevista
  • Auditoría y roles incluidos
